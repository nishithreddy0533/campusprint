# Requirements Document

## Introduction

CampusPrint is a full-stack web application that digitizes the college Xerox and stationery shop ordering workflow. Students submit documents, specify printing requirements, receive a server-computed cost estimate, simulate payment, and track order progress in real time — all without waiting in a physical queue. Shop staff manage the complete order queue through a centralized dashboard, updating statuses and communicating rejections with reasons.

## Glossary

- **Order**: A single printing request submitted by a student, identified by a unique orderId (token).
- **Token / OrderId**: A unique identifier auto-generated by the system when an order is created; used by students to track their order.
- **PrintType**: The color mode chosen for printing — either `bw` (black and white) or `color`.
- **Binding**: The physical finishing option chosen — `none`, `staple`, or `spiral`.
- **OrderStatus**: The lifecycle state of an order — one of `received`, `processing`, `ready`, or `collected`.
- **PaymentStatus**: Whether the simulated payment for an order has been completed — `pending` or `paid`.
- **Staff**: An authorized shop employee who manages and processes orders via the staff dashboard.
- **Student**: A college student who submits printing orders via the student-facing interface.
- **DynamoDB Local**: A locally-running instance of Amazon DynamoDB used during development.
- **S3**: Amazon Simple Storage Service, used for storing uploaded document files in production.
- **ECR**: Amazon Elastic Container Registry, used to store Docker images.
- **ECS**: Amazon Elastic Container Service, used to run the containerized backend in production.
- **Polling**: Repeated HTTP requests from the client at a fixed interval to detect server-side state changes without a persistent WebSocket connection.
- **Cost Calculation**: Server-side computation of order price: (pages × copies × per-page rate) + binding surcharge. B&W rate = ₹2/page, Color rate = ₹8/page, staple surcharge = ₹5, spiral surcharge = ₹20.
- **ENV**: Environment variable — a runtime configuration value supplied outside the codebase.

## Requirements

### Requirement 1 — Document Upload

**User Story:** As a student, I want to upload my document to the platform, so that the shop can access it without me physically handing it over.

#### Acceptance Criteria

1. WHEN a student submits a file for upload, THE CampusPrint system SHALL accept files with MIME types matching PDF (`application/pdf`), common image types (`image/jpeg`, `image/png`), and Microsoft Word formats (`application/msword`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`).
2. WHEN a student submits a file exceeding 20 MB, THE CampusPrint system SHALL reject the upload with an HTTP 400 response and a descriptive error message.
3. WHEN a student submits a file of an unsupported type, THE CampusPrint system SHALL reject the upload with an HTTP 400 response and a descriptive error message.
4. WHEN a valid file is uploaded successfully, THE CampusPrint system SHALL store the file and return a file reference URL usable in subsequent order creation.
5. WHERE the `STORAGE_BACKEND` environment variable is set to `local`, THE CampusPrint system SHALL store uploaded files on the local disk rather than Amazon S3.

---

### Requirement 2 — Order Creation and Cost Calculation

**User Story:** As a student, I want to specify printing requirements and see a calculated cost, so that I know what I will pay before confirming.

#### Acceptance Criteria

1. WHEN a student submits a new order with studentName, studentContact, fileUrl, printType, pages, copies, and binding, THE CampusPrint system SHALL create the order record and return the computed cost along with the generated orderId.
2. THE CampusPrint system SHALL compute cost exclusively on the server side using the formula: `cost = pages × copies × (printType === 'color' ? 8 : 2) + (binding === 'staple' ? 5 : binding === 'spiral' ? 20 : 0)`.
3. WHEN a student submits an order with pages less than 1, copies less than 1, or a missing required field, THE CampusPrint system SHALL return an HTTP 400 response with a field-level error message.
4. WHEN an order is created successfully, THE CampusPrint system SHALL set the initial `orderStatus` to `received` and `paymentStatus` to `pending`.
5. WHEN a student includes specialInstructions in an order, THE CampusPrint system SHALL store those instructions alongside the order record.

---

### Requirement 3 — Payment Simulation

**User Story:** As a student, I want to complete a simulated payment step, so that my order moves forward in the workflow.

#### Acceptance Criteria

1. WHEN a student calls the payment endpoint for an existing order with `paymentStatus` of `pending`, THE CampusPrint system SHALL update `paymentStatus` to `paid` and return the updated order.
2. WHEN a student calls the payment endpoint for an order that does not exist, THE CampusPrint system SHALL return an HTTP 404 response.
3. WHEN a student calls the payment endpoint for an order that is already `paid`, THE CampusPrint system SHALL return an HTTP 400 response indicating the order is already paid.
4. WHEN payment is confirmed, THE CampusPrint system SHALL record the `updatedAt` timestamp on the order.

---

### Requirement 4 — Order Tracking

**User Story:** As a student, I want to track my order's status in real time, so that I know when to come to the shop to collect it.

#### Acceptance Criteria

1. WHEN a student requests an order by orderId, THE CampusPrint system SHALL return the full order record including current `orderStatus`, `paymentStatus`, `cost`, and `estimatedCompletionTime`.
2. WHEN the order does not exist, THE CampusPrint system SHALL return an HTTP 404 response.
3. WHEN a student's order `orderStatus` changes on the server, THE CampusPrint frontend SHALL reflect the updated status within 5 seconds via client-side polling.
4. WHEN a student's order is in `ready` status, THE CampusPrint frontend SHALL display a prominent in-app notification banner informing the student to collect the order.

---

### Requirement 5 — Order History and Token Lookup

**User Story:** As a student, I want to view all my past orders and look up any order by token, so that I can reference previous transactions.

#### Acceptance Criteria

1. WHEN a student queries orders by `studentContact`, THE CampusPrint system SHALL return all orders associated with that contact, sorted by `createdAt` descending.
2. WHEN a student provides a valid token (orderId) to the lookup endpoint, THE CampusPrint system SHALL return the matching order record.
3. WHEN no orders exist for the given `studentContact`, THE CampusPrint system SHALL return an empty array with HTTP 200.

---

### Requirement 6 — Staff Dashboard and Order Management

**User Story:** As a staff member, I want a centralized dashboard showing all orders, so that I can process them efficiently.

#### Acceptance Criteria

1. WHEN a staff member accesses the orders list endpoint, THE CampusPrint system SHALL return all orders sorted by `createdAt` descending, with support for `status` and `search` query parameters.
2. WHEN a staff member filters by `status`, THE CampusPrint system SHALL return only orders matching that `orderStatus`.
3. WHEN a staff member provides a `search` term, THE CampusPrint system SHALL return orders whose token number or student name contains the search term (case-insensitive).
4. WHEN the orders list exceeds 50 items, THE CampusPrint frontend SHALL paginate results showing 20 items per page with navigation controls.
5. WHEN a staff member views an order detail, THE CampusPrint system SHALL include the document file reference, all printing requirements, cost, payment status, and current order status.

---

### Requirement 7 — Order Status Updates and Rejection

**User Story:** As a staff member, I want to update order statuses and reject invalid orders, so that students receive accurate progress information.

#### Acceptance Criteria

1. WHEN a staff member updates an order's status, THE CampusPrint system SHALL accept only the valid transitions: `received` → `processing`, `processing` → `ready`, `ready` → `collected`.
2. WHEN a staff member attempts to set status to `processing` on an order whose `paymentStatus` is `pending`, THE CampusPrint system SHALL return an HTTP 400 response indicating payment has not been confirmed.
3. WHEN a staff member rejects an order, THE CampusPrint system SHALL require a non-empty `rejectionReason` string and set `orderStatus` to `rejected`.
4. WHEN an order is rejected, THE CampusPrint system SHALL record the `rejectionReason` and the `updatedAt` timestamp.
5. WHEN a staff member provides an invalid status transition, THE CampusPrint system SHALL return an HTTP 400 response describing the invalid transition.

---

### Requirement 8 — Staff Authentication

**User Story:** As a staff member, I want to log in with credentials, so that the dashboard is protected from unauthorized access.

#### Acceptance Criteria

1. WHEN a staff member submits the correct username and password (read from environment variables `STAFF_USERNAME` and `STAFF_PASSWORD`), THE CampusPrint system SHALL return a session token valid for the current browser session.
2. WHEN a staff member submits incorrect credentials, THE CampusPrint system SHALL return an HTTP 401 response.
3. WHEN an unauthenticated request is made to any staff API route, THE CampusPrint system SHALL return an HTTP 401 response.
4. WHEN the `STAFF_USERNAME` or `STAFF_PASSWORD` environment variable is absent at startup, THE CampusPrint system SHALL terminate with a clear error message identifying the missing variable.

---

### Requirement 9 — Error Handling and API Robustness

**User Story:** As a developer/operator, I want every API route to handle errors gracefully, so that the server never crashes on bad input or missing resources.

#### Acceptance Criteria

1. WHEN any API route receives malformed or missing required parameters, THE CampusPrint system SHALL return HTTP 400 with a structured JSON error body containing a `message` field.
2. WHEN any API route cannot find a requested resource, THE CampusPrint system SHALL return HTTP 404 with a structured JSON error body.
3. WHEN an unexpected server-side error occurs, THE CampusPrint system SHALL return HTTP 500 with a generic error message and SHALL log the full error server-side without exposing stack traces to the client.
4. WHEN the server starts, THE CampusPrint system SHALL validate all required environment variables and exit with a descriptive error message listing missing variables if any are absent.

---

### Requirement 10 — Environment Configuration and Deployment

**User Story:** As a developer/operator, I want the app to be fully configurable via environment variables and runnable via Docker, so that it can be deployed consistently across environments.

#### Acceptance Criteria

1. THE CampusPrint repository SHALL include a `.env.example` file listing every environment variable the application depends on, with placeholder values and inline comments.
2. WHERE the `STORAGE_BACKEND` environment variable is set to `local`, THE CampusPrint system SHALL store and serve files from a local directory without requiring AWS credentials.
3. WHERE the `DYNAMODB_ENDPOINT` environment variable is set, THE CampusPrint system SHALL connect to that endpoint rather than the AWS-managed DynamoDB service.
4. THE CampusPrint repository SHALL include a `Dockerfile` that builds and runs the backend on Node.js 20.
5. THE CampusPrint repository SHALL include a `docker-compose.yml` that starts the backend and a DynamoDB Local instance together for local development.
6. THE CampusPrint repository SHALL include a `README.md` with step-by-step instructions for local Docker Compose setup and separate AWS ECR/ECS deployment steps.

---

### Requirement 11 — Cost Calculation Serialization (Pretty-Print & Round-Trip)

**User Story:** As a developer, I want order data to be correctly serializable to and from JSON, so that records stored in DynamoDB and returned from the API are always consistent.

#### Acceptance Criteria

1. WHEN an order object is serialized to JSON and then deserialized, THE CampusPrint system SHALL produce an object equal to the original in all fields.
2. THE CampusPrint system SHALL include a pretty-printer function that formats an order record as a human-readable JSON string.
3. WHEN the pretty-printer output is parsed, THE CampusPrint system SHALL produce an order object equal to the original.
